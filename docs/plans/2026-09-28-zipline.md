# Zipline — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A public file-sharing service for the owner only — upload a file, get a short link anyone can open — with no other homelab service exposed.

**Architecture:** A dedicated 50 GB disk at `/srv/zipline` holds uploads and Postgres data. Zipline + PostgreSQL + a **Tailscale sidecar** run on `docker-host`; Zipline shares the sidecar's network namespace, so it lives on its **own tailnet node** (`zipline`). A single `tailscale funnel` on that node publishes it; the tailnet policy permits funnel for **that node's IP only**.

**Tech Stack:** Docker Compose, `ghcr.io/diced/zipline:4.8.0`, `postgres:16`, `tailscale/tailscale:v1.102.4`, Tailscale funnel.

**Spec:** `docs/specs/2026-09-28-zipline-design.md`

## Global Constraints

- **The funnel must target the `zipline` node only** — never `docker-host`.
- **`nodeAttrs.target` takes an address/tag, not a hostname** (`"zipline"` ⇒ *invalid address*).
- **Uploads/DB never on the root disk** — always `/srv/zipline`.
- **Registration OFF, anonymous uploads OFF, no public gallery.**
- **Images pinned**; secrets only in the git-ignored `.env`.
- The auth key is a tailnet credential — never commit it.

## Review Focus

- **Nothing else became public** — pinned by Task 4 Step 2 (server-side serve/funnel
  status) and Task 5 (an off-tailnet check).
- **The right device may be funneled** — pinned by the `nodeAttrs` IP matching the
  sidecar's `tailscale ip -4`.
- **Uploads land on the dedicated disk** — pinned by Task 1 Steps 3–4.
- **The dashboard tile** — verified via `/api/services`, never the HTML shell.

## Task 1: Disk + stack

- [ ] **Step 1** — `qm set 100 --scsi3 local-lvm:50,discard=on,ssd=1,iothread=1`;
  confirm the guest sees `/dev/sdd` (sda=OS, sdb=music, sdc=backup).
- [ ] **Step 2** — `mkfs.ext4 -L zipline /dev/sdd`; fstab by UUID; mount
  `/srv/zipline`; owner `1000:1000` (pgdata `999:999`).
- [ ] **Step 3 (REVIEW FOCUS)** — create `/srv/zipline/{uploads,public,themes,pgdata}`
  **on the disk** (they must not be relative paths in the compose).
- [ ] **Step 4** — write `stacks/zipline/{compose.yaml,.env.example,README.md}`;
  generate `CORE_SECRET` + `POSTGRESQL_PASSWORD`; put `TS_AUTHKEY` in `.env`
  (git-ignored), `chmod 600`.

## Task 2: Deploy (tailnet-only)

- [ ] **Step 1** — `docker compose up -d`; expect `zipline`, `zipline-db`
  (healthy), `zipline-ts`.
- [ ] **Step 2** — the sidecar joined as its own node:
  `docker exec zipline-ts tailscale status` → a line for `zipline`.
- [ ] **Step 3** — reachable from a tailnet device:
  `curl -sI http://zipline.tail91459b.ts.net:3000/` → `301` (to `/dashboard`).

## Task 3: Owner — first-run setup

- [ ] **Step 1 (owner)** — open `http://zipline.tail91459b.ts.net:3000/` and create
  the super-admin as `admin`. (Legacy default if no setup page: `administrator`/`password`.)
- [ ] **Step 2 (owner)** — in the admin UI: **registration OFF**, **anonymous
  uploads OFF**, no public gallery, set upload/expiry defaults.

## Task 4: Funnel — permission, then enable *(owner + agent)*

- [ ] **Step 1 (owner)** — Access controls → **Add Funnel to policy**, then edit the
  target to the sidecar's IP:
  ```json
  "nodeAttrs": [ { "target": ["100.78.80.41"], "attr": ["funnel"] } ]
  ```
- [ ] **Step 2 (agent)** — enable it:
  ```sh
  docker exec zipline-ts tailscale funnel --bg --https=443 http://127.0.0.1:3000
  docker exec zipline-ts tailscale funnel status   # "Funnel on: …"
  ```
- [ ] **Step 3 (REVIEW FOCUS)** — prove nothing else changed:
  ```sh
  tailscale serve status   # on docker-host → every mapping says "(tailnet only)"
  tailscale funnel status  # on docker-host → no "# Funnel on"
  ```

## Task 5: Verify from OFF the tailnet *(owner)*

- [ ] **Step 1 (owner)** — from a phone with **Tailscale off** (mobile data):

  - `https://docker-host.tail91459b.ts.net` → **fails**.
  > A fetch from a tailnet-connected device proves nothing — both URLs resolve.
